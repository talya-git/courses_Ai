הסבר פשוט · Context

מה זה Context (הקשר)?

כל המידע והטקסט שהמודל מקבל ומביא בחשבון בעת יצירת התשובה.

ההקשר כולל את:

  • הטקסט של השאלה או הבקשה הנוכחית ששלחת.
  • קבצים, מסמכים או חומרים נלווים שצירפת לבקשה.
  • היסטוריית השיחה הקודמת באותו חלון שיחה.
  • הנחיות המערכת שהוגדרו למודל.

חלון הקשר (Context Window)

לכל מודל שפה יש מגבלה הנקראת "חלון הקשר": כמות המידע המרבית (במילים או ב-Tokens) שהמודל מסוגל לקרוא, לזכור ולעבד בבת אחת לצורך מתן התשובה.

לכן בשקף הקודם "ההקשר רק גדל": כל צעד בלולאה נשלח שוב עם כל ההיסטוריה, וחלון ההקשר מתמלא.

[הסבר פשוט] שאלה שעולה תמיד: 'מה זה Context? זה החומר שאני מצרפת לפרומפט?' התשובה: גם, אבל לא רק. הקשר הוא כל המידע שהמודל מקבל ומביא בחשבון: השאלה הנוכחית, קבצים שצירפת, היסטוריית השיחה באותו חלון, והנחיות המערכת. לכל מודל יש מגבלה שנקראת חלון הקשר (Context Window): הכמות המרבית של מידע, במילים או ב-Tokens, שהוא יכול לעבד בבת אחת.

הסבר פשוט · System Instructions

דוגמה: קובץ הנחיות מערכת

# הנחיות מערכת - עוזר וירטואלי
## 1. תפקיד וזהות
- אתה עוזר וירטואלי מקצועי, אדיב ויעיל.
- תפקידך לספק תשובות מדויקות, ברורות וממוקדות.
## 2. כללי שפה וסגנון
- שפת ברירת המחדל היא עברית תקנית וברורה.
- יש להימנע משפה פוגענית, סלנג חריף או ביטויים לא מכובדים.
## 3. דיוק ואמינות מידע
- בספק לגבי עובדה – ציין את מידת הוודאות.
- אין להמציא עובדות, ציטוטים או מקורות.
## 4. גבולות ואחריות
- אין לספק ייעוץ משפטי, רפואי או פיננסי מחייב.
- יש לשמור על פרטיות המשתמשים.
## 5. תהליך מענה מומלץ
1. קרא את הבקשה בעיון. 2. נסח תשובה קצרה תחילה.
3. ודא שהתשובה עונה על כל סעיפי השאלה.

מה רואים כאן

  • הנחיות המערכת הן חלק מההקשר: הן נשלחות למודל בכל פנייה.
  • מבנה ברור עם כותרות (Markdown) עוזר למודל להבין מה חשוב.
  • חמישה חלקים: תפקיד, שפה, דיוק, גבולות, ותהליך מענה.
  • אפשר להעתיק את המבנה ולהתאים אותו לכל מערכת.
[הסבר פשוט] דוגמה לקובץ הנחיות מערכת (System Instructions) מובנה, המיועד להגדרת התנהגות של מודל שפה עבור אפליקציה או מערכת אינטראקטיבית. חמישה חלקים: 1. תפקיד וזהות. 2. כללי שפה וסגנון (עברית תקנית, טון רגוע וענייני, בלי שפה פוגענית, חלוקה לסעיפים בנושא מורכב). 3. דיוק ואמינות (לציין מידת ודאות, לא להמציא עובדות, מונחים מדויקים). 4. גבולות ואחריות (בלי ייעוץ משפטי, רפואי או פיננסי מחייב; שמירה על פרטיות). 5. תהליך מענה (לקרוא בעיון, לנסח קצר ואז להרחיב, לוודא שכל סעיפי השאלה נענו).

תכנון Tools

Tools הם ממשק למודל, לא עטיפה ל־API

Agent–Computer Interface

הסיפור מ־SWE-bench

כש־Anthropic בנו סוכן ל־SWE-bench, הם השקיעו יותר זמן בשיפור ה־Tools מאשר ב־prompt.

המודל טעה בנתיבים יחסיים אחרי שעבר תיקייה. הפתרון לא היה הוראה ב־prompt: שינו את ה־Tool כך שיקבל רק נתיב מוחלט. הטעות נעלמה.

עקרונות מהשטח

  • לאחד: schedule_event אחד במקום list_users + list_events + create_event
  • שמות שמובנים למודל: שם ותפקיד, לא UUID
  • Namespacing: asana_search, jira_search
  • פלט מוגבל: עימוד, סינון, מצב concise
  • שגיאות שמסבירות מה לעשות, לא stack trace

אם עובד חדש היה מתבלבל מה־Tool, גם המודל יתבלבל.

מקורות: Anthropic, "Building effective agents" (2024) ו־"Writing effective tools for agents" (2025).

המונח ACI, Agent–Computer Interface, בא מעולם ה־HCI: כמו שמשקיעים בממשק למשתמש, צריך להשקיע בממשק למודל. הדוגמה של הנתיבים המוחלטים היא poka-yoke: מתכננים את ה־Tool כך שאי אפשר לטעות בו. עקרון האיחוד: אם כל פעם שהמודל קובע פגישה הוא קורא לשלושה Tools ברצף, עדיף Tool אחד שעושה את שלושתם. זה חוסך סיבובים, טוקנים והזדמנויות לטעות. Claude Code, למשל, מגביל כברירת מחדל את גודל התוצאה של Tool, וחותך פלט ארוך מדי. ה־Tool הוא חלק מה־Harness, לא חלק מהמודל.

איך Claude הגיע ל-49% במבחן SWE-bench Verified

מהו המבחן?

מבחן סטנדרטי שבודק אם מודל יכול לפתור משימות תכנות אמיתיות מתוך מאגרי קוד פתוח ב-GitHub (כמו scikit-learn).

  • המודל מקבל סביבת עבודה ותיאור בעיה (PR Description).
  • עליו לאתר את הקבצים, לשחזר את השגיאה, לתקן, ולהריץ בדיקות.

מודל חכם + מעטפת פשוטה

במקום מערכת מסובכת עם מאות כלים, נתנו למודל עצמאות ושני כלים כלליים בלבד:

  • Bash Tool: הרצת פקודות, סקריפטים ובדיקות.
  • Edit Tool (str_replace_editor): צפייה בתיקיות, יצירת קבצים, והחלפת מחרוזת ישנה בחדשה.

דוגמה מהמאמר

שגיאה ב-scikit-learn: חסר פרמטר store_cv_values.

  • בחן את מבנה התיקיות.
  • כתב סקריפט ששחזר את השגיאה (TypeError).
  • הוסיף את הפרמטר החסר בהחלפה מדויקת.
  • הריץ שוב ווידא שהתיקון הצליח.

אתגרים: משימות מורכבות דורשות מאות שלבים ועשרות אלפי Tokens, ולכן התהליך יקר וארוך. בנוסף, המודל נבחן מול בדיקות נסתרות (Hidden tests), ולפעמים הוא חושב שהצליח כשבפועל הפתרון לא עמד בכל התנאים.

[הסבר פשוט] המאמר מתאר איך Anthropic שיפרה את Claude 3.5 Sonnet המעודכן במבחן SWE-bench Verified עד 49%. שאלות שעלו: 'מה זה אומר שיש לו כלים לעריכה?' – לסוכן יש יכולת טכנית לגשת למערכת הקבצים של הפרויקט, לצפות בקבצים, ליצור קבצים ולבצע שינויים מדויקים בקוד המקור. בניגוד למודל שיחה שרק כותב קוד בצ'אט, כלי עריכה מאפשר לו לבצע את התיקונים בפועל בתוך קובצי הפרויקט, כמו מתכנתת. 'זאת אומרת שהוא עושה את זה דרך הטרמינל?' – כן. באמצעות כלי ה-Bash הוא מריץ פקודות בסביבת עבודה מבודדת: חוקר תיקיות, מריץ סקריפטים שמשחזרים שגיאות, ומוודא שהבדיקות עוברות.

הסבר פשוט · כתיבת Tools

איך כותבים כלים טובים לסוכן

בתוכנה רגילה פונקציה מקבלת קלט מדויק ומחזירה פלט קבוע. סוכן משתמש בכלים לפי שיקול דעתו, ויש לו מגבלת הקשר. כלי שתוכנן לא נכון גורם לו להתבלבל, לטעות ולבזבז משאבים.

1אב-טיפוסבונים כלים בסיסיים ומחברים אותם דרך שרת מקומי כדי לבדוק בפועל.

MCP הוא חיבור USB-C לבינה מלאכותית

Model Context Protocol הוא תקן פתוח שמחבר בין יישומי AI (כמו Claude או ChatGPT) לבין מערכות, כלים ומקורות מידע חיצוניים. כמו ש-USB-C הוא חיבור אחיד לכל המכשירים, MCP הוא חיבור אחיד בין מודלים למערכות.

מה MCP מאפשר?

  • חיבור למקורות מידע: קבצים מקומיים, מסדי נתונים ארגוניים, יומנים (Google Calendar) ותוכנות ניהול (Notion).
  • שילוב כלים חיצוניים: מנועי חיפוש, סביבות פיתוח ותוכנות עיצוב.
  • ביצוע משימות: גישה לנתונים מעודכנים וביצוע פעולות בשם המשתמש.

למה זה חשוב?

  • למפתחים: כותבים חיבור פעם אחת, והוא מתאים לכל מקום שתומך בתקן.
  • ליישומי ה-AI: יוצאים מעבר למידע הסטטי שעליו אומנו.
  • למשתמשים: עוזרים חכמים שעובדים עם הכלים והנתונים הקיימים שלהם.
[הסבר פשוט] MCP הוא תקן פתוח (קוד פתוח) לחיבור יישומי AI למערכות, כלים ומקורות מידע. האנלוגיה: USB-C. כשם שחיבור USB-C מספק תקן אחיד לחיבור רכיבים שונים למחשב, MCP מספק תקן אחיד שמאפשר למודלים להתחבר למערכות שונות. למפתחים זה חוסך זמן: לא צריך לכתוב חיבור ייעודי לכל תוכנה בנפרד.

מה הקשר בין ה-Client ל-Server? שיחת טלפון לפי כללים

שני חצאי גשר

  • ה-Client יושב בתוך התוכנה שבה את עובדת. מתרגם את בקשת המודל לשפת MCP ושולח החוצה.
  • ה-Server יושב מחוץ לאפליקציה. מבצע את הפעולה האמיתית (מושך הודעות מ-Slack, קורא קובץ מהדיסק) ומחזיר תוצאה.

למה ההפרדה? ה-Host לא יודע להתחבר ישירות לכל תוכנה בעולם. בזכות MCP, המפתחים של Slack כותבים Server אחד, וכל אפליקציה עם Client מתחברת אליו מיד.

Client → Server · בקשה (JSON-RPC)

{ "jsonrpc": "2.0", "id": 1,
  "method": "tools/call",
  "params": { "name": "read_file",
    "arguments": { "path": "/documents/notes.txt" } } }

Server → Client · תשובה

{ "jsonrpc": "2.0", "id": 1,
  "result": { "content": [
    { "type": "text", "text": "File content..." } ] } }

דוגמה: שרת לניהול קבצים (Filesystem Server) עם הכלים read_file, list_directory, write_file.

[הסבר פשוט] הקשר בין ה-Client ל-Server הוא כמו שיחת טלפון לפי כללים מוגדרים מראש (JSON-RPC). ה-Client אומר: 'שלום סרבר סלאק, המודל מבקש לדעת מה ההודעות האחרונות בערוץ X, הנה הפרמטרים בשפת MCP'. ה-Server עונה: 'קיבלתי, ניגשתי לסלאק, הנה ההודעות בפורמט MCP'. ה-Client תופס את התשובה ומעביר למודל. דוגמה לשרת: Filesystem Server שמצהיר על read_file, list_directory ו-write_file. כשהמודל צריך לקרוא קובץ, ה-Client שולח tools/call, השרת קורא את הקובץ מהדיסק ומחזיר את התוכן. דוגמאות נוספות: שרת GitHub (פתיחת Issue, קריאת Pull Request), שרת SQL (הרצת שאילתות), שרת לניהול משימות.

Tool annotations

רמזים שה־Harness יכול להשתמש בהם להחלטות הרשאה. רמז, לא הבטחה: אל תסמכו עליהם משרת לא מוכר.

ניהול דינמי של כל ה-Tokens שנכנסים למודל בכל רגע: הנחיות, היסטוריה, כלים, תוצאות כלים, קבצים ונתונים מ-MCP.

איפה בדיוק ה-Hook נכנס?

ה-Hook הוא לא חלק מהמודל. הוא רכיב במערכת שמקיפה ומנהלת את המודל (ה-Agent Harness), ויושב בנקודות מעבר בתוך לולאת העבודה.

PreToolUse · לפני הרצת כלי

בין הרגע שהמודל אומר "אני רוצה להריץ rm -rf" לבין ההרצה בפועל. אם הפקודה מסוכנת, ה-Hook מחזיר deny והיא נחסמת.

PostToolUse · אחרי הרצת כלי

לפני שהתוצאה חוזרת למודל: בדיקת התוצאה, תיעוד ללוג, או הוספת מידע שיעזור לתקן שגיאה.

Stop · כשהמודל סיים

אנלוגיה: עובד במשרד

  • המודל הוא העובד שמקבל החלטות ומבקש לבצע פעולות.
  • הכלים הם הפעולות שהוא יכול לבצע: לשלוח מכתב, להדפיס מסמך.
  • ה-Hook הוא השומר שעומד לצידו: עוצר כל הוראה לרגע, בודק לפי כללים קבועים, ומאשר, דוחה או מוסיף הערה.
[הסבר פשוט] מהם Hooks: פקודות מותנות שמוגדרות על ידי המפתחת ומופעלות אוטומטית בנקודות זמן במחזור החיים של Claude Code. כשאירוע מתרחש, המערכת בודקת אם הוא תואם לתנאי (Matcher), ומעבירה את נתוני האירוע ב-JSON ל-Hook. סוגים: Command (סקריפט מקומי), HTTP (בדיקה בכתובת חיצונית), MCP Tool, ו-Prompt/Agent (בדיקה בעזרת מודל). אפשר להגדיר ברמת המשתמש או הפרויקט, עם תנאי if, וגם להריץ ברקע (Async). ולוגיקת הלולאה: קבלת משימה, פנייה למודל, החלטה על כלי, ביצוע, וחוזר חלילה. ה-Hook נשתל בנקודות המעבר בלי לשנות את המודל.

    r"\brm\s+-\w*r\w*\s+(/|~|\*)",     # rm -rf / ~ *
    r"(?i)\bdrop\s+(table|database)\b",  # the Replit case
    r"\bgit\s+push\s+.*--force",
    r"\b(curl|wget)\b.*\|\s*(ba|z)?sh",  # pipe to shell

async def block_dangerous(input_data, tool_use_id, context):
    cmd = input_data["tool_input"].get("command", "")
    if any(re.search(p, cmd) for p in DANGEROUS):
        return {"hookSpecificOutput": {
            "hookEventName": "PreToolUse",
            "permissionDecision": "deny",
            "permissionDecisionReason": f"Blocked: {cmd}"}}
    return {}

options = ClaudeAgentOptions(
    hooks={"PreToolUse": [HookMatcher(matcher="Bash",

המסקנה

מחסומי אבטחה (Guardrails) הם לא פתרון מושלם, כי תוקפים מוצאים דרכים עוקפות. האחריות על המפתחת והמשתמש: לא ליצור את השילוב של שלושת הרכיבים יחד.

[הסבר פשוט] המאמר של Simon Willison מגדיר את 'השילוש הקטלני': גישה למידע פרטי + חשיפה לתוכן לא מהימן + יכולת תקשורת חיצונית. הבעיה: מודלי שפה מתוכנתים לציית להנחיות שהם קוראים, ולא מבחינים בין הוראה לתוכן. מכיוון שמשתמשים רבים מחברים היום כלים (כמו MCP) בלי להיות מודעים לסיכון, האחריות הגדולה היא להימנע מהשילוב של שלושת הרכיבים יחד.

סיכום

חמישה דברים לקחת מכאן

1. המודל מחליט. ה־Harness מבצע, מגביל ומתעד.

2. Tools הם ממשק למודל. MCP נותן גישה, Skill נותן נוהל, Hook נותן אכיפה.

3. Multi-Agent הוא דרך לחלק הקשר. שווה רק כשתתי־המשימות עצמאיות.

4. הקשר ועלות הם בעיות של ה־Harness: compaction, מטמון, טעינה לפי הצורך.

5. SDK חוסך קוד, לא אחריות. הרשאות, אבטחה, ניטור והערכה נשארים שלכם.

לחזור על חמש הנקודות, ולחזור לשאלה מתחילת הקורס: איפה הייתה צריכה להיות ההגנה ב־Replit? לא ב־prompt. בהרשאות, ב־Hook ובהפרדת סביבות. כלומר ב־Harness.
